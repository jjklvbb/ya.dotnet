## Учебный проект WebApiProject

### Запуск проекта

1. Клонировать репозиторий: `git clone https://github.com/jjklvbb/ya.dotnet.git`
2. Перейти в папку `../ya.dotnet/WebApiProject`
3. Собрать проект: `dotnet build`
4. Запустить тесты: `dotnet test`
5. Запустить приложение: `dotnet run`
6. Приложение будет доступно следующему адресу: `http://localhost:5168/`
7. Открыть Swagger по адресу: `http://localhost:5168/swagger/`

###  API событий

Реализован RESTful Web API проект для управления событиями на **C# (.NET 10)** с использованием **ASP.NET Core Web API**.

API предоставляет полный CRUD-набор операций над событиями:

- `GET /events` — получить список всех событий (с поддержкой фильтрации и пагинации)
- `GET /events/{id}` — получить событие по ID  
- `POST /events` — создать новое событие  
- `PUT /events/{id}` — обновить существующее событие  
- `DELETE /events/{id}` — удалить событие  

При создании и обновлении события проверяются следующие правила:
- Поле `title` обязательно и не может быть пустым.
- Поля `startAt` и `endAt` обязательны.
- Значение `endAt` должно быть позже `startAt`.

#### Фильтрация и пагинация

| Параметр   | Тип      | Обязательный | По умолчанию | Описание                         |
| ---------- | -------- | ------------ | ------------ | -------------------------------- |
| `title`    | string   | нет          | —            | Фильтр по названию события       |
| `from`     | DateTime | нет          | —            | События начиная с указанной даты |
| `to`       | DateTime | нет          | —            | События до указанной даты        |
| `page`     | int      | нет          | `1`          | Номер страницы, значение ≥ 1     |
| `pageSize` | int      | нет          | `10`         | Размер страницы, значение ≥ 1    |


```http
# Получить все события
GET /events

# Фильтрация по названию и датам
GET /events?title=концерт&from=2026-10-01&to=2026-12-31

# Пагинация (вторая страница по 5 событий)
GET /events?page=2&pageSize=5

# Комбинированный запрос
GET /events?title=встреча&page=1&pageSize=10
```

### API бронирований

Для событий реализована возможность создания бронирований с отложенной фоновой обработкой.

#### Модель Booking

Бронирование содержит следующие поля:

* `id` (`Guid`) — уникальный идентификатор брони;
* `eventId` (`Guid`) — идентификатор события;
* `status` (`BookingStatus`) — текущий статус брони;
* `createdAt` (`DateTime`) — дата и время создания брони;
* `processedAt` (`DateTime?`) — дата и время обработки брони.

При создании бронь автоматически получает уникальный `Id`, статус `Pending` и текущее время в `CreatedAt`.

Возможные статусы бронирования:

* `Pending` — бронь создана и ожидает обработки;
* `Confirmed` — бронь подтверждена;
* `Rejected` — бронь отклонена.

#### Создание брони

```http
POST /events/{id}/book
```

Создаёт бронь для указанного события.

При успешном запросе:

* возвращается `202 Accepted`;
* в теле ответа возвращается информация о созданной брони;
* в заголовке `Location` возвращается ссылка на ресурс брони `/bookings/{bookingId}`.

Если событие не найдено, возвращается `404 Not Found`.

#### Получение брони

```http
GET /bookings/{id}
```

Возвращает текущее состояние брони.

При успешном запросе возвращается `200 OK`.

Если бронь не найдена, возвращается `404 Not Found`.

### Фоновая обработка бронирований

Обработка бронирований выполняется с помощью `BackgroundService`.

Фоновый сервис периодически получает бронирования со статусом `Pending`.

Для каждой такой брони:

1. выполняется искусственная задержка в 2 секунды, имитирующая обращение к внешней системе;
2. статус изменяется с `Pending` на `Confirmed`;
3. поле `ProcessedAt` заполняется временем обработки;
4. обновлённая бронь сохраняется в in-memory хранилище.

#### Пример сценария

Создать событие:

```http
POST /events
```

Создать бронь:

```http
POST /events/{eventId}/book
```

Ответ содержит:

```text
HTTP 202 Accepted
Location: /bookings/{bookingId}
```

Сразу после создания можно получить состояние брони:

```http
GET /bookings/{bookingId}
```

Статус:

```text
Pending
```

Через несколько секунд повторить запрос:

```http
GET /bookings/{bookingId}
```

Статус изменится на:

```text
Confirmed
```

После обработки поле `processedAt` будет заполнено.

### Формат ответов при ошибках

При возникновении исключений глобальный middleware перехватывает их и возвращает единообразный ответ в формате **Problem Details** с соответствующим HTTP-статусом:

* `400 Bad Request` — ошибка валидации;
* `404 Not Found` — ресурс не найден;
* `500 Internal Server Error` — непредвиденная ошибка.

Пример `400 Bad Request`:

```json
{
  "type": null,
  "title": "Bad request",
  "status": 400,
  "detail": "Модель не валидна. Подробности: The Title field is required.",
  "instance": null,
  "extensions": {}
}
```

Пример `404 Not Found`:

```json
{
  "type": null,
  "title": "Resource not found",
  "status": 404,
  "detail": "Событие по ключу 6cb53659-8f98-4e23-b7c9-b7411e77a0c8 не найдено.",
  "instance": null,
  "extensions": {}
}
```

Пример `500 Internal Server Error`:

```json
{
  "type": null,
  "title": "Internal server error",
  "status": 500,
  "detail": "Attempted to divide by zero.",
  "instance": null,
  "extensions": {}
}
```

### Тестирование

Для проекта используются юнит-тесты на **xUnit**.

Тестами покрыты:

* CRUD-операции с событиями;
* фильтрация и пагинация событий;
* успешные и неуспешные сценарии `EventService`;
* создание и изменение состояния `Booking`;
* успешные и неуспешные сценарии `BookingService`;
* in-memory хранилище бронирований;
* фоновая обработка бронирований.
