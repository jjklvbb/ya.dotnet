# О репозитории

В этом репозитории располагаются проекты по обучению **«Продвинутая разработка на C# и .NET»**.

- Учебный проект находится в папке **WebApiProject**
- В папке **theoryPractice** находятся проекты, которые использовались при изучении теории

## Учебный проект WebApiProject

RESTful Web API для управления событиями и бронированиями на **C# (.NET 10)** с использованием **ASP.NET Core Web API**.

Проект поддерживает:

- CRUD-операции с событиями;
- фильтрацию и пагинацию;
- создание и получение бронирований;
- ограничение количества мест на событии;
- защиту от овербукинга при конкурентных запросах;
- параллельную фоновую обработку бронирований;
- единообразную обработку ошибок через Problem Details;
- хранение событий и бронирований в PostgreSQL;
- доступ к данным через репозитории;
- управление схемой PostgreSQL через EF Core Migrations;
- интеграционные тесты репозиториев на реальном PostgreSQL через Testcontainers.

## Запуск проекта

1. Клонировать репозиторий: `git clone https://github.com/jjklvbb/ya.dotnet.git`
2. Перейти в папку `../ya.dotnet/WebApiProject`
3. Для запуска требуется PostgreSQL.

Пример строки подключения в `appsettings.json`:

```json
"ConnectionStrings": {
  "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
}
```

Запустить PostgreSQL можно через предоставленный docker compose-файл:

`docker compose up -d`

### Миграции

Схема базы данных управляется через EF Core Migrations.

Создать новую миграцию:

```bash
dotnet ef migrations add MigrationName
```

Применить миграции вручную:

```bash
dotnet ef database update
```

Удалить последнюю миграцию, если она ещё не была применена:

```bash
dotnet ef migrations remove
```

При запуске приложения неприменённые миграции автоматически применяются через `db.Database.Migrate()`.

4. Собрать проект: `dotnet build`
5. Запустить тесты: `dotnet test`
6. Запустить приложение: `dotnet run`
7. Приложение будет доступно следующему адресу: `http://localhost:5168/`
8. Открыть Swagger по адресу: `http://localhost:5168/swagger/`

# API событий

Доступны следующие операции:

* `GET /events` — получить список событий с фильтрацией и пагинацией;
* `GET /events/{id}` — получить событие по ID;
* `POST /events` — создать событие;
* `PUT /events/{id}` — обновить событие;
* `DELETE /events/{id}` — удалить событие.

## Модель события

Событие содержит:

* `id` (`Guid`) — уникальный идентификатор;
* `title` (`string`) — название;
* `description` (`string?`) — описание;
* `startAt` (`DateTime`) — дата и время начала;
* `endAt` (`DateTime`) — дата и время окончания;
* `totalSeats` (`int`) — общее количество мест;
* `availableSeats` (`int`) — текущее количество свободных мест.

При создании события:

```text
AvailableSeats = TotalSeats
```

Пример создания события:

```http
POST /events
```

```json
{
  "title": "Концерт",
  "description": "Тестовое событие",
  "startAt": "2026-10-10T18:00:00",
  "endAt": "2026-10-10T21:00:00",
  "totalSeats": 3
}
```

При создании и обновлении события проверяются следующие правила:

* `title` обязателен и не может быть пустым;
* `startAt` и `endAt` обязательны;
* `endAt` должен быть позже `startAt`;
* `totalSeats` при создании обязателен и должен быть больше нуля.


---

## Фильтрация и пагинация

| Параметр   | Тип      | Обязательный | По умолчанию | Описание                         |
| ---------- | -------- | ------------ | ------------ | -------------------------------- |
| `title`    | string   | нет          | —            | Фильтр по названию события       |
| `from`     | DateTime | нет          | —            | События начиная с указанной даты |
| `to`       | DateTime | нет          | —            | События до указанной даты        |
| `page`     | int      | нет          | `1`          | Номер страницы, значение ≥ 1     |
| `pageSize` | int      | нет          | `10`         | Размер страницы, значение ≥ 1    |

Примеры:

```http
GET /events

GET /events?title=концерт&from=2026-10-01&to=2026-12-31

GET /events?page=2&pageSize=5

GET /events?title=встреча&page=1&pageSize=10
```

# API бронирований

Для событий реализовано создание бронирований с последующей фоновой обработкой.

## Модель Booking

Бронирование содержит:

* `id` (`Guid`) — уникальный идентификатор брони;
* `eventId` (`Guid`) — идентификатор события;
* `status` (`BookingStatus`) — строковое значение `Pending`, `Confirmed` или `Rejected`;
* `createdAt` (`DateTime`) — время создания;
* `processedAt` (`DateTime?`) — время завершения обработки.

Возможные состояния:

* `Pending` — бронь создана и ожидает обработки;
* `Confirmed` — бронь подтверждена;
* `Rejected` — бронь отклонена.

При создании бронь получает уникальный `Id`, статус `Pending` и текущее время в `CreatedAt`.

---

## Создание брони

```http
POST /events/{id}/book
```

При успешном бронировании:

* одно свободное место резервируется у события;
* создаётся новая бронь со статусом `Pending`;
* возвращается `202 Accepted`;
* в заголовке `Location` возвращается адрес `/bookings/{bookingId}`.

Возможные ответы:

* `202 Accepted` — бронь успешно создана;
* `404 Not Found` — событие не найдено;
* `409 Conflict` — свободных мест больше нет.

---

## Получение брони

```http
GET /bookings/{id}
```

Возвращает текущее состояние бронирования.

Возможные ответы:

* `200 OK` — бронь найдена;
* `404 Not Found` — бронь не существует.

# Защита от овербукинга

Для предотвращения овербукинга в `BookingService.CreateBookingAsync` используется статический `SemaphoreSlim`.

`BookingService` зарегистрирован как scoped, поэтому экземпляров сервиса может быть несколько. Статический семафор обеспечивает общую синхронизацию между ними.

В критической секции:
1. событие загружается из БД;
2. проверяется наличие свободного места;
3. уменьшается `AvailableSeats`;
4. создаётся `Booking`;
5. одним `SaveChangesAsync()` сохраняются оба изменения.


## Пример сценария с овербукингом

Создаётся событие с `totalSeats = 3`.

После создания:

- `TotalSeats = 3`;
- `AvailableSeats = 3`.

Далее выполняются четыре запроса:

1. Первая бронь → `202 Accepted`, `AvailableSeats = 2`.
2. Вторая бронь → `202 Accepted`, `AvailableSeats = 1`.
3. Третья бронь → `202 Accepted`, `AvailableSeats = 0`.
4. Четвёртая бронь → `409 Conflict`.

Таким образом, количество успешных бронирований не может превысить количество мест на событии.

# Параллельная фоновая обработка

Бронирования со статусом `Pending` обрабатываются сервисом `BookingBackgroundService`.

`BookingBackgroundService` является singleton, поэтому для получения scoped-зависимостей используется `IServiceScopeFactory`.

Сначала в отдельном scope через `IBookingRepository` загружаются идентификаторы Pending-бронирований. Затем каждая бронь обрабатывается параллельно в собственном scope. Внутри scope используются `IEventRepository` и `IBookingRepository`, которые работают через общий scoped `AppDbContext`.

Для параллельного запуска используется `Task.WhenAll`.

После окончания задержки:

* если событие существует — бронь переводится в `Confirmed`;
* если событие было удалено — бронь переводится в `Rejected`;
* при неожиданной ошибке бронь переводится в `Rejected`, а зарезервированное место возвращается через `ReleaseSeats()`.

# Формат ответов при ошибках

Глобальный middleware перехватывает исключения и возвращает единообразный ответ в формате **Problem Details**.

Используются следующие HTTP-статусы:

* `400 Bad Request` — ошибка валидации;
* `404 Not Found` — ресурс не найден;
* `409 Conflict` — отсутствуют свободные места;
* `500 Internal Server Error` — непредвиденная ошибка.

Пример `400 Bad Request`:

```json
{
  "type": null,
  "title": "Bad request",
  "status": 400,
  "detail": "Модель не валидна. Подробности: The Title field is required.",
  "instance": null,
  "extensions": {}
}
```

Пример `404 Not Found`:

```json
{
  "type": null,
  "title": "Resource not found",
  "status": 404,
  "detail": "Событие по указанному идентификатору не найдено.",
  "instance": null,
  "extensions": {}
}
```

Пример `409 Conflict`:

```json
{
  "type": null,
  "title": "Conflict",
  "status": 409,
  "detail": "No available seats for this event",
  "instance": null,
  "extensions": {}
}
```

# Тестирование

Для проекта используются тесты на **xUnit**.

Для юнит-тестов используется EF Core InMemory provider.
Каждый тестовый класс использует отдельную InMemory-базу с уникальным именем.
В тестах конкурентности каждый параллельный запрос выполняется
в отдельном DI-scope со своим AppDbContext.

Тестами покрыты:

* CRUD-операции с событиями;
* фильтрация и пагинация;
* валидация событий;
* создание и изменение состояния `Booking`;
* успешные и неуспешные сценарии `BookingService`;
* уменьшение `AvailableSeats` после создания брони;
* попытка бронирования при отсутствии свободных мест;
* возврат места через `ReleaseSeats()` после отклонения брони;
* возможность повторного бронирования освобождённого места;
* защита от овербукинга при конкурентных запросах;
* сценарий с 5 местами и 20 параллельными запросами;
* уникальность `Id` при конкурентном создании бронирований;
* переход фоновой брони в `Confirmed`;
* переход брони в `Rejected`, если событие было удалено;
* фоновая обработка бронирований.

Дополнительно создан отдельный проект `EventApi.IntegrationTests` с интеграционными тестами репозиториев.

Интеграционные тесты используют настоящий PostgreSQL, который автоматически запускается через Testcontainers. Для их выполнения требуется запущенный Docker.

Все интеграционные тесты используют один PostgreSQL-контейнер. Перед каждым тестом схема базы данных очищается, после чего миграции применяются заново через `MigrateAsync()`.

Интеграционными тестами проверяются:

- применение миграций;
- все методы `EventRepository`;
- фильтрация событий по `title`, `from` и `to`;
- комбинация фильтров;
- сортировка и пагинация;
- все методы `BookingRepository`;
- сохранение изменений сущностей в PostgreSQL.

Запустить все тесты:

```bash
dotnet test ya.dotnet.slnx
```

Запустить только интеграционные тесты:

```bash
dotnet test EventApi.IntegrationTests/EventApi.IntegrationTests.csproj
```
