# Event Booking — микросервисная система бронирования

Учебный проект на **C# / .NET 10 и ASP.NET Core Web API**. Система управляет пользователями, мероприятиями и бронированиями. Микросервисы используют отдельные базы PostgreSQL и обмениваются событиями через Apache Kafka без прямых HTTP-вызовов друг к другу.

## Состав репозитория

| Каталог | Назначение |
|---|---|
| `src/Services/Users` | Регистрация, вход, выдача JWT |
| `src/Services/Events` | Управление мероприятиями и доступными местами |
| `src/Services/Bookings` | Создание, просмотр и отмена бронирований |
| `src/Shared/Messaging.Contracts` | Контракт `BookingConfirmed` и имя Kafka-топика |
| `tests` | Тесты актуальных сервисов (xUnit) |
| `legacy` | Код и тесты исходного монолита, не входящие в активное решение |

Каждый сервис состоит из проектов **Domain, Application, Infrastructure и Api** (слой представления), имеет собственные `DbContext`, миграции EF Core и PostgreSQL. Активное решение — `ya.dotnet.slnx`.

## Архитектура и обмен сообщениями

```text
                       ┌─────────────┐
                       │ Users.Api   │ → usersdb
                       │ выдаёт JWT  │
                       └─────────────┘
                              │ JWT
                   ┌──────────┴──────────┐
                   ▼                     ▼
              Events.Api            Bookings.Api
                  │                     │
               eventsdb              bookingsdb
                  ▲                     │
                  │                     │ BookingConfirmed
                  └──── Kafka ◄─────────┘
```

1. **Users** регистрирует пользователей и выдаёт JWT через `POST /auth/login`.
2. **Bookings** создаёт бронь со статусом `Pending`. Фоновый обработчик переводит её в `Confirmed`, сохраняет изменение в PostgreSQL и публикует `BookingConfirmed` в топик `booking-confirmed`.
3. **Events** получает сообщение и уменьшает `AvailableSeats` у соответствующего мероприятия. Обработанные `BookingId` сохраняются в отдельной таблице для защиты от повторного списания места.

Формат Kafka-сообщения `BookingConfirmed`:

```json
{
  "BookingId": "22222222-2222-2222-2222-222222222222",
  "EventId": "11111111-1111-1111-1111-111111111111",
  "UserId": "33333333-3333-3333-3333-333333333333",
  "SeatsCount": 1,
  "ConfirmedAt": "2026-11-16T12:00:00Z"
}
```

Одна бронь сейчас резервирует одно место. Ключ Kafka-сообщения — `EventId`. Оба сервиса используют общий проект `Messaging.Contracts`. Users выдаёт токены, а Events и Bookings проверяют их по одинаковым `Jwt:Secret`, `Jwt:Issuer` и `Jwt:Audience`.

## Запуск

Необходимы **Docker Desktop** и Docker Compose. Для сборки и тестов вне контейнеров — **.NET SDK 10**.

1. Клонируйте репозиторий:

   ```bash
   git clone https://github.com/jjklvbb/ya.dotnet.git
   cd ya.dotnet
   ```

   Для запуска версии девятого спринта переключитесь на `sprint-9`, если её изменения ещё не включены в `main`:

   ```bash
   git checkout sprint-9
   ```

2. Создайте файл `.env` в корне репозитория (он исключён из Git):

   ```env
   JWT_SECRET=replace-with-a-random-secret-longer-than-32-bytes
   ```

   Замените пример собственным секретом длиной не менее 32 байт.

3. Запустите компоненты:

   ```bash
   docker compose up -d --build
   docker compose ps
   ```

Docker Compose поднимает три API, три PostgreSQL, Kafka и ZooKeeper. Миграции EF Core применяются API при запуске. Для Kafka настроена проверка готовности (`healthcheck`), от которой зависит запуск Events и Bookings.

| Сервис | Swagger | PostgreSQL (порт хоста) |
|---|---|---|
| Users | http://localhost:5101/swagger | 5433 |
| Events | http://localhost:5102/swagger | 5434 |
| Bookings | http://localhost:5103/swagger | 5435 |

Kafka доступна по адресу `localhost:9092` с хоста и `kafka:29092` внутри Docker.

Адрес брокера задаётся параметром `Kafka:BootstrapServers`, а группа подписчиков Events — `Kafka:ConsumerGroup`. В Docker Compose соответствующие переменные — `Kafka__BootstrapServers` и `Kafka__ConsumerGroup`. При запуске Events создаёт топик `booking-confirmed` при его отсутствии; при временной недоступности Kafka предусмотрены повторные попытки.

Остановка без удаления данных: `docker compose down`.

## API и права доступа

| Сервис | Маршруты | Доступ |
|---|---|---|
| Users | `POST /auth/register`, `POST /auth/login` | Публичный |
| Events | `GET /events`, `GET /events/{id}` | Публичный |
| Events | `POST /events`, `PUT /events/{id}`, `DELETE /events/{id}` | Только Admin |
| Bookings | `POST /bookings`, `GET /bookings/{id}`, `DELETE /bookings/{id}` | Требуется JWT |

Получать и отменять бронирование может только его владелец или администратор. При обращении к чужой брони возвращается HTTP `403 Forbidden`. Неверные учётные данные при входе возвращают HTTP `401 Unauthorized`.

**Мероприятие** содержит `Id`, `Title`, `Description`, `StartAt`, `EndAt`, `TotalSeats`, `AvailableSeats`. При создании все места доступны; даты начала и окончания передаются в UTC. `GET /events` поддерживает фильтры `title`, `from`, `to` и пагинацию `page`, `pageSize`.

**Бронь** содержит идентификаторы мероприятия и пользователя, статус и даты создания/обработки. Статусы: `Pending`, `Confirmed`, `Rejected`, `Cancelled`. Создание — `POST /bookings` с телом `{"eventId":"<guid>"}`. Для пользователя действует лимит **10 активных бронирований** (`Pending` и `Confirmed`). Идентификатор пользователя берётся из JWT.

В Swagger защищённых API используйте **Authorize** и токен, полученный через Users.

## Проверка работы

1. Через Users зарегистрируйте администратора и выполните вход.
2. С JWT администратора создайте мероприятие через Events с `totalSeats: 10` и будущими датами.
3. Создайте бронь через `POST /bookings`, указав `eventId` мероприятия.
4. Проверьте `GET /bookings/{id}`: статус должен стать `Confirmed`.
5. Проверьте `GET /events/{id}`: число свободных мест должно уменьшиться **с 10 до 9** после обработки Kafka-сообщения.

Это сквозная проверка доставки `BookingConfirmed` через Kafka. Положительный сценарий проверялся локально.

## Ограничения текущей реализации

- Подтверждение бронирования в Bookings и резервирование места в Events происходят асинхронно через Kafka. Между этими операциями возможна временная несогласованность.
- Если мероприятие не найдено или свободных мест нет, Events записывает предупреждение и фиксирует смещение Kafka-сообщения без резервирования места. Автоматического согласования статуса брони с Bookings пока нет.
- Отмена подтверждённой брони изменяет её статус в Bookings, но **не возвращает место в Events**. Событие возврата мест пока не реализовано.
- Сохранение подтверждённой брони в PostgreSQL и публикация сообщения в Kafka не являются атомарной операцией. При сбое после сохранения возможна потеря публикации. Если событие доставлено повторно, Events проверяет `BookingId`, чтобы не списать место дважды.

Проект предназначен для учебной демонстрации микросервисной архитектуры. Конфигурация Docker и возможность регистрации пользователей с ролью Admin без дополнительных ограничений не предназначены для промышленной эксплуатации.
